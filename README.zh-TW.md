# Token Beggar（Token 乞丐）

**把每個 token 都乞討回來。答案一樣，token 更少。**

[English](README.md) | [繁體中文](README.zh-TW.md)

![Token Beggar 示範](assets/demo.gif)

我是給終端機程式代理用的技能，只有一個習慣：大模型動手之前，先問有沒有更便宜的路線能做得一樣好。對話模型會把你的提示拆成子任務，每個子任務挑「品質夠用、最便宜」的供應商、模型與 effort：交給 worker 裡的小模型、交給 `agy` 這類外部工具的命令列，或自己做。設計、找根本原因與最後的答覆，留給你選的那個模型。

```
/plugin marketplace add Arthur031221/Token-Beggar
/plugin install token-beggar@token-beggar
```

重新啟動代理，或執行 `/reload-plugins`，再執行 `token-beggar doctor` 確認 hook 正常運作。需要 Python 3.10 以上，只用標準函式庫。

我出手的每一則回覆結尾，你會看到一行：

```
Token Beggar: about 1.6x fewer tokens than Opus 5.5 high alone (est. 86k vs 135k) | exact edits | routed 1: haiku low x1
```

第一個數字（86k）是實際計數：主對話加上所有 worker 的輸入、輸出與快取。第二個數字是這個計數乘上我量測到的比值，所以是估計值，也會標明 est.。外部工具用掉的 token 另外列出，因為它們不佔你的對話額度。如果這類任務量測不到好處，這一行會直說，不會硬宣稱省了多少。

## 省多少

下面的數字都是對話端 token（你的方案實際計費的部分），對話模型是 Opus 5.5，effort 為 high。7 類共 21 個任務，每個任務跑 3 次，三組的提示與工具相同：模型單獨做、我的第一版（固定的分類表），以及這個版本的動態路由。

| 組別 | 每個任務的 token | 每個任務的費用 | 品質 |
| --- | --- | --- | --- |
| 單獨做 | 105,690 | $0.152 | 0.96 |
| 固定表（v0.1） | 101,446（少 1.04 倍） | $0.122 | 0.96 |
| **動態路由（v0.2）** | **93,501（少 1.13 倍）** | $0.133 | **0.97** |

動態路由在品質相同或更好的情況下用的 token 更少，所以取代了固定表。不過就金額來看固定表更便宜：$0.122 對 $0.133。金額是依用掉 token 的模型單價加權，所以兩種量法對各組的排序可能不同。兩個都有量測，也都放在儲存庫裡。分類結果：

| 類別 | 單獨做 | 固定表 | 動態 | 動態對單獨做 | 品質（單獨 / 固定表 / 動態） |
| --- | --- | --- | --- | --- | --- |
| 多檔案功能 | 160,462 | 135,395 | 112,791 | **1.42x** | 1.00 / 1.00 / 1.00 |
| 機械式修改 | 116,715 | 112,538 | 98,096 | **1.19x** | 1.00 / 1.00 / 1.00 |
| 找 bug 根本原因 | 146,363 | 124,514 | 130,712 | 1.12x | 1.00 / 1.00 / 1.00 |
| 閱讀與摘要 | 69,501 | 72,089 | 64,778 | 1.07x | 0.89 / 0.86 / 0.92 |
| 程式碼審查 | 92,207 | 85,928 | 89,695 | 1.03x | 0.83 / 0.87 / 0.93 |
| 設計 | 62,063 | 55,779 | 62,190 | 1.00x | 1.00 / 1.00 / 0.97 |
| 一般程式碼 | 92,519 | 123,880 | 96,247 | 0.96x | 1.00 / 1.00 / 1.00 |

老實說，混合任務的整體是 1.13 倍，多檔案工作是 1.42 倍，不是 10 倍。這些任務都不大，每個 worker 都要付一筆固定的啟動成本，所以任務越大省得越多。低於約 1.15 倍的數字，我都視為和沒省沒有差別：每組只跑 3 次，這個差距落在我看到的波動之內。

v0.1 的閱讀品質下滑（0.89 降到 0.86）是一個綜合題的一項檢查點，再加上雜訊。動態路由在同樣的任務上是 0.92。路由規則是在這 21 個任務上調了六輪（第一張軟性的卡片完全不會分派，每個版本都記錄在 `data/measured.json`），所以這量的是這個設定，無法預測你的情況。

### 頁尾的比值

頁尾需要「你用的模型、effort、任務種類」對應的比值，我全部量過：4 個模型（Opus 5.5、Sonnet 5.5、Haiku 5.5、Fable 5.1）、5 種 effort（low 到 max）、8 種任務，每種一個小任務，各跑「單獨做」與「用技能」，共 288 次列印模式的 JSON 輸出。單一格子雜訊很大，所以頁尾引用的是某模型某任務種類的合併比值（把所有量過的 effort 的 token 加總）。比值大於 1 代表用技能 token 更少。

| 任務種類 | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 | Fable 5.1 |
| --- | --- | --- | --- | --- |
| 多檔案功能 | 1.73 | 0.62 | 0.98 | 1.71 |
| 精確修改 | 1.57 | 1.13 | 1.60 | 1.42 |
| 一個函式加測試 | 1.48 | 1.24 | 1.38 | 1.43 |
| 設計 | 1.14 | 1.44 | 1.21 | 1.27 |
| 讀完回答 | 1.26 | 1.07 | 0.93 | 1.11 |
| 審查 | 0.87 | 1.40 | 1.05 | 1.21 |
| 修 bug | 1.04 | 0.98 | 0.93 | 1.36 |
| 摘要多個檔案 | 0.89 | 0.74 | 1.04 | 0.93 |

低於 1.15 時，頁尾會寫「差不多」或「單獨做可能更省」；沒有量過的比值就只印計數。引用數字之前請先知道：

- 對話模型是 Sonnet 5.5 時，多檔案功能（0.62）與摘要多個檔案（0.74）反而更費：worker 的啟動成本比省下的還多。頁尾會照實說。
- Fable 5.1 只量了 low、high 與 max。medium 與 xhigh 在 `data/measured.json` 與頁尾都標為 `interpolated`（內插），使用合併比值。其他格子都是實際跑出來的。
- 不用技能時，一個任務的中位數 token 在 max effort 是 medium 的約 3.4 倍，xhigh 是約 1.5 倍。小工作用 `max` 是我看到最大的單一 token 開銷。
- 每個格子每組只跑一次。合併比值內的波動範圍（`cell_min`、`cell_max`）在資料裡。

### 外部工具

在 PATH 上有 `agy` 且已登入的情況下，我量了三項「把大量工作交給外部工具應該能省對話 token」的工作：把每個 carrier 模組讀成一份排序清單、寫初稿、對設計給第二意見。每組跑 3 次，Opus 5.5 high。

| 工作 | 單獨做的對話 token | 用技能 | 比值 | 交給 agy | 品質（單獨 / 用技能） |
| --- | --- | --- | --- | --- | --- |
| 讀多個檔案 | 59,097 | 61,714 | 0.96x | 3 / 3 | 1.00 / 1.00 |
| 初稿 | 97,103 | 97,870 | 0.99x | 1 / 3 | 1.00 / 1.00 |
| 第二意見 | 38,826 | 42,160 | 0.92x | 0 / 3 | 0.75 / 0.67 |

這沒有顯示出節省。工作交出去之後（讀檔那項，每次都交出去，agy 共用了 14,886 個 token），對話端總量仍和自己做持平，因為這裡的檔案很小：對話模型為派工、提示與檢查付出的成本，和自己讀差不多。第二意見從來沒有交出去。我預期輸入達到數十萬 token 時差距會拉開，但我沒量過，所以不宣稱。我量測的機器上 Gemini 命令列沒有登入，所以 Gemini 完全沒量。

### 量測方式

- 一個小型 Python 商店專案。21 個任務：機械式修改、閱讀、一般程式碼、多檔案功能、除錯、設計、審查各 3 個。
- 每一組的提示、允許的工具、對話模型與 effort 都相同。
- 程式碼任務用隱藏的檢查加專案測試計分。回答類任務由不知道哪組產出文字的盲評者，依檢查清單計分。
- token 是對話與所有子代理的輸入 + 輸出 + 快取讀取 + 快取寫入，取自代理自己的 JSON（`modelUsage`）。外部工具的 token 另外計。
- 原始執行：[`benchmark/results/raw`](benchmark/results/raw)（路由）、[`matrix/raw`](benchmark/results/matrix/raw)（頁尾比值）、[`agy/raw`](benchmark/results/agy/raw)（外部工具）。表格在 [`report.md`](benchmark/results/report.md)。
- 重現：`python3 benchmark/run.py --arms alone,beggar,dynamic`，再跑 `score.py` 與 `report.py`。矩陣是 `matrix.py run|score|fit`，外部工具的工作是 `agy_bench.py`。完整跑一次路由以牌價算約 $20。

## 安裝

不想安裝、只想試一個工作階段，可以複製儲存庫，用 `--plugin-dir ./Token-Beggar` 啟動代理。

</details>

## 我怎麼運作

1. **拆解。** 一個 hook 在工作階段第一個像樣的提示加入選單，之後每個提示加一行提醒。選單列出你能用的每個供應商、模型與 effort，附上各自擅長與不擅長的事、能力分數與價格。太短的提示和斜線指令什麼都不加。對話模型把提示拆成子任務。
2. **逐項選擇。** 決策規則會問規模、模糊程度、風險、要讀多少，以及有沒有測試能驗證結果。能過關的組合中最便宜的勝出。一行答案或小修改留在原地，因為 worker 啟動時有自己的基本上下文。
3. **守住上限。** 你對話用的模型與 effort，是同一家廠商模型的上限。你用 Sonnet medium，就不會有工作送到 Opus 或更高的 effort。其他供應商不設上限，除非你在提示裡說，例如「agy max flash」讓 agy 只用 flash 系列，「no gemini」本次工作階段關掉 gemini。
4. **便宜地檢查。** 跑一次測試或 `git diff --stat`，不重讀全部。判斷與最後的答覆留給對話模型。
5. **回報。** 由 Stop hook 加上面的頁尾，不是模型寫的：hook 直接數對話記錄，所以數字不會是文字編出來的。

說 `/token-beggar` 或「token beggar」，可以對沒有自動觸發的提示手動啟用我。

### 外部工具當作路由

PATH 上的 `agy`、`gemini`、`codex` 與 MCP 伺服器都會出現在選單。`token-beggar inventory` 會列出它們，並偵測各工具的模型（`agy models`）。優先順序是代理自己的模型先，其次 Codex，再來 Gemini，所以大量讀取與初稿可以外送，需要這段對話、要改檔案或有風險的工作則不行。我絕不傳送機密：看起來像金鑰的檔名與文字會被拒絕。

```
token-beggar ask agy --model gemini-3.8-flash-low --file 'src/**/*.py' "list every public function with its arguments"
token-beggar cap agy flash
```

`--file` 接受萬用字元與目錄。工具回應用量上限時，我會解析錯誤訊息裡的重置時間，並在那之前把該工具（或該模型）從選單拿掉。訊息沒寫時間的話，額度用完算五小時，登入問題算一天。外部的答案只是草稿，對話模型用之前會先看過。

### 壓縮

不用設定就能運作。代理在依上下文視窗算出的點壓縮，預設比視窗少 33k token。我自己找出這個點（`token-beggar window` 會印出），所以你不需要設壓縮視窗的環境變數。你設了的話，我就用你的值。

- **常常檢查。** 每個提示，以及長回合中每次工具呼叫之後。
- **提早警告。** 到壓縮點的 87.5%，或離壓縮點 30k token 時（取先到者），我請對話模型判斷是否正在某一步的中間（修改尚未驗證、跨檔案的改動做到一半、計畫進行中），並用 `token-beggar note` 存一份筆記：目標、已完成、下一步，幾行即可。模型沒寫的話，機械式擷取（原始請求、改過的檔案、最後的指令）是備案。
- **延後中途的壓縮。** `PreCompact` hook 回傳結束碼 2，可以延後自動壓縮。我最多延後 3 次，每次是視窗的 5%，絕不靠近到離代理拒絕請求的水位不到 5k token，而且只在筆記標明中途時才延後。手動 `/compact` 從不攔。
- **讀回來。** 壓縮之後，工作階段開始的 hook 會把筆記連同選單放回去。壓縮前很久才寫的筆記會被標為舊的。

我用列印模式在真實工作階段測過：視窗 100k，逐一讀 8 份長文件。警告在 67k 壓縮點的 47k 和 63k 兩次出現，模型在中途寫了筆記，兩次壓縮被延後，代理在 95k 壓縮了一次，之後模型從筆記接續，並正確列出八個檔案的第一個字。限制：worker 內做的修改我看不到，所以不為它們延後，也不會列進筆記。一次工具結果若大於壓縮點前的餘裕，可以直接跳過那個點。代理把視窗限制在 100k 到 1M。見 [docs/architecture.md](docs/architecture.md)。

### 檢查與查看它做了什麼

`token-beggar doctor` 列出會悄悄讓路由失效的事：不支援的 Python、無法寫入的狀態目錄、被環境變數強制的 worker 模型、hook 的錯誤記錄，以及 hook 進入點能不能跑。有問題時結束碼為 1。

`token-beggar stats` 讀你自己最近的工作階段（預設 7 天，用 `--days N` 修改）。每個 worker 模型會印出跑了幾個 worker、用了多少 token、花了多少錢，以及同樣的 token 用啟動它的模型來跑會花多少。最後一欄是委派搬動金額的上限，不是淨節省。

### 模型

`data/models.json` 列出各模型家族、價格與預設 effort。GitHub Action 每週從廠商公開的模型頁面更新，已安裝的副本則在本機每週檢查一次。`data/profiles.json` 放能力與成本資料，以及產生選單用的決策規則。

## 類似工具

我在做這個之前看過這些，也保留了它們做得好的部分。差異是事實陳述，不是排名。

| 工具 | 做什麼 | 我的不同 |
| --- | --- | --- |
| 本機路由代理（例如 musistudio 的專案） | 依情境把代理的請求轉到其他供應商的代理伺服器 | 我不碰 API 路徑，而是用代理自己的子代理在工作階段內路由，並以對話模型作為上限 |
| 子代理的模型變數與 agent 檔的 `model:` | 把子代理固定在一個模型 | 靜態：不評估任務與上限，也無法每次呼叫選 effort |
| ccusage 類的用量表 | 事後回報花費 | 我在花錢之前動作，倍數來自基準測試而不是你的歷史 |
| 省 token 的指南與上下文技能 | 較短的提示、較小的上下文、較少的讀取 | 和我相容。我只改變誰來做 |

## 限制

- 小任務因為 worker 啟動成本，節省有限。低於約 1.15 倍我無法和沒省區分。
- 路由比較涵蓋一個專案、一個對話模型與 effort（Opus 5.5、high）。頁尾比值涵蓋四個模型和五種 effort，每格跑一次，單一格子雜訊大，Fable 有 16 格是內插的。
- 動態路由用的 token 比固定表少，但金額較高（每個任務 $0.133 對 $0.122）。如果你是依金額而不是額度計費，請對你的任務組合確認這個取捨。
- 在我測的小檔案上，沒有顯示外部工具帶來節省，Gemini 命令列也沒量。
- 頁尾是依比值估計的。裡面的計數是真的，「vs」後面的數字並不是你這個任務的量測。代理有時在最後一則訊息寫入前就執行 Stop hook，我會等最多 4 秒，仍沒出現就印「at least」。
- hook 看不到對話模型，所以先從對話記錄讀模型，再看執行中代理程序的啟動旗標、環境變數與設定。都沒說是哪個模型時，卡片會說上限未知，並要我絕不超過自己的模型。
- worker 和任何工作階段一樣會載入你專案的記憶檔。基準測試專案沒有，所以那份成本不在數字裡。
- 由模型評分的任務可能評錯。基準測試裡的檢查是為了抓出這點，不是消除它。
